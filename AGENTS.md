# Agent guidance

## Build & test
- Build: `dotnet build GrillMaster.slnx`
- Run (planner from `appsettings.json`): `dotnet run --project src/GrillMaster.Console`
- Tests: each test project is an MTP project — run it directly:
  - `dotnet run --project tests/GrillMaster.UnitTests`
  - `dotnet run --project tests/GrillMaster.IntegrationTests`
  - `dotnet run --project tests/GrillMaster.EndToEndTests`
  - `dotnet run --project tests/GrillMaster.PerformanceTests`
- `tests/GrillMaster.Core.Testing` is a shared classlib (WireMock mocks, `TestData`, the `grill-menus.json` fixture) referenced by the test projects; it has no tests of its own.
- Do NOT use `dotnet test` — its MTP mode is broken with xunit v3 on this SDK (exits non-zero, runs 0 tests).

## Analyzer rules
- `Directory.Build.props` sets `AnalysisMode=AllEnabledByDefault` and `TreatWarningsAsErrors=true`.
- Keep the build at **0 warnings**; any new warning fails the build.
- Suppressions live in `.editorconfig` (CA1724, CA1062, CA1814, CA1859, CA1002, CA2227, CA2225, CA1849, CA13xx, IDE0023/IDE0024, IDE03xx, …). Add new ones there, not in code.

## Layout
- `src/` — three projects.
   - `GrillMaster.Domain/` — pure, dependency-free models (`GrillSize`, `GrillPiece`, `GrillMenuItem`, `GrillMenu`, `GrillPiecePlacement`, `GrillRound`, `GrillPlan`) + value types (`Centimeters`, `SquareCentimeters`, `Point`); namespace `GrillMaster.Domain`.
    - `GrillMaster.Application/` — the application layer; namespace `GrillMaster.Application`. `Features/Menus/` = grill menu API client + wire DTOs (namespace `GrillMaster.Application.Features.Menus[.Models]`); `Features/Plans/` = grilling planners + engine (namespaces `GrillMaster.Application.Features.Plans[.Planners]`; `PlannerNames` = the well-known planner-name constants, the single source of truth for `IGrillPlanner.Name`); `Settings/` = `IGrillMasterSettings`/`GrillMasterSettings` (bound to the `GrillMaster` configuration section: `GrillMenuApiUrl`, `Planner`) + the single `GrillMasterSettingsValidator` (`IValidateOptions<GrillMasterSettings>` checking the URL is an absolute URI and the planner is a known `PlannerNames` name); `GrillMasterApp.cs` + `DependencyConfigurator.cs` at the project root — `AddApplicationDependencies()` registers the options (validate-on-start, exposed as `IGrillMasterSettings`), the menu `HttpClient` + `GrillMenuService`, all eight planners as `IGrillPlanner` singletons, and `GrillMasterApp`.
    - `GrillMaster.Console/` — the executable, namespace `GrillMaster`: `Program.cs` (`Run()` builds the host via `HostBuilder.CreateHost` and runs it with `host.RunAsync()`), `HostBuilder.cs` (the composition root — `CreateHost` builds the Generic Host, pins the content root to `AppContext.BaseDirectory` so `appsettings.json` loads from the app's own directory, then wires everything in DI via `AddLogging` (Serilog) and `AddAppServices` (application dependencies + the hosted service); `ConfigureConsoleLogging` sets the all-white console sink; there is no CLI, all settings come from configuration), `GrillMasterHostedService.cs` (runs the `GrillMasterApp` when the host starts, then stops the application so `host.RunAsync()` returns), `appsettings.json`.
- Dependency chain: `Console` → `Application` → `Domain`.
- The host is built in `HostBuilder.CreateHost` — no runtime objects are passed into DI registrations; the whole application graph (`GrillMenuService`, the planners, `GrillMasterApp`) is constructor-injected. `GrillMasterApp` picks the planner by matching `IGrillPlanner.Name` against the configured `Planner` from its injected `IEnumerable<IGrillPlanner>`. The pipeline runs as the `GrillMasterHostedService` hosted service, so `host.RunAsync()` drives the whole app. Misconfiguration (bad URL, unknown planner) fails fast when the host starts (options validation); `Program.Run` catches the `OptionsValidationException`, logs each failure as an error line, and exits 1 instead of dumping a stack trace.
- Logging is Serilog via `Serilog.Extensions.Hosting`: `HostBuilder.CreateHost` builds a per-host logger from the `Serilog` configuration section (`ReadFrom.Configuration`) plus the `configureLogging` hook, and registers it with `builder.Services.AddSerilog(logger, dispose: false)` (the `Log.Logger` static is never touched; `dispose: false` keeps the host shutdown from disposing the logger and its sinks). Serilog backs `Microsoft.Extensions.Logging`, so app code injects `ILogger<T>` (category = the type's full name). `builder.Logging.ClearProviders()` keeps the default providers from double-writing. The console app configures a console sink with template `{Message:lj}{NewLine}` (no timestamp/level) and an all-white `SystemConsoleTheme` (every `ConsoleThemeStyle` → white foreground), so console output is plain white report lines; the `Microsoft`/`System` level overrides (framework noise off) live in the `Serilog` section of `appsettings.json`. `GrillMasterApp` logs one `{MenuName}: {RoundCount} rounds` event per menu (menus processed in name order) plus a `Total: {TotalRounds} rounds` event.
- `tests/` — xunit v3 on MTP. `GrillMaster.Core.Testing/` is the shared classlib: `Infra/` holds the WireMock mocks, `Core/` holds `TestCaseSerializer` (namespace `GrillMaster.Core.Testing.Core`), and `grill-menus.json` is the real 15-menu API fixture (exposed via `TestData.GrillMenusJson`). `UnitTests`, `IntegrationTests` and `PerformanceTests` reference it. `IntegrationTests` references the `Console` project and runs the whole flow in-process: `Fixtures/GrillMasterFactory` creates a `GrillMasterApp` (the hosted app: exposes the per-test in-memory `Sink`, `ExitCode`, and `RunAsync`, which mirrors `Program.Run` — application failures are logged and reported as exit code 1, API failures surface as the raw exception) — the same `HostBuilder.CreateHost` as `Program`, with the settings supplied via `services.Configure<GrillMasterSettings>`, the API pointed at WireMock and logging routed to the in-memory sink + the xUnit test output (assert via `app.Sink.Should().HaveMessage(...)` from `Serilog.Sinks.InMemory.Assertions`). Test classes derive from `Tests/GrillMasterTestBase`, which owns the `GrillMenuApiMock` and provides `CreateApp`/`RunGrillMaster`. `Tests/GrillMasterSettingsValidatorTests` validates misconfiguration the same way — sink assertions on the error line + `ExitCode` 1. The API client is not tested in isolation — failure scenarios (API errors, empty menus) are validated on the console log response a real user would see. `PerformanceTests/` keeps its baseline machinery in `Base/` (`PerformanceResultStore` — loads/saves the committed `performanceResults.json` and captures the git commit on save; `Base/Models` — the result records). `EndToEndTests` is the real end-to-end: a single test that launches the built console app as an external process exactly the way a user runs it — no mocks, configuration from the app's own `appsettings.json` (the live API; the apphost is copied to the test output by the `Console` project reference) — captures stdout/stderr and validates the report lines: one "{menu}: {rounds} rounds" per menu in name order, ending with a "Total: {rounds} rounds" line equal to their sum.

## Conventions
- Grilling planners implement `IGrillPlanner` and are selected by name; the 30×20 cm grill is the fixed frame. Planner names are the `PlannerNames` constants — never string literals (planner `Name` properties, tests, settings validation all use them); the configured `Planner` setting must be one of `PlannerNames.All`.
- Physical measurements use the domain value types, not raw ints: `Centimeters` (lengths/widths/heights), `SquareCentimeters` (areas), `Point` (x/y coordinates — a `GrillPiecePlacement` carries a `Point Position`, not `X`/`Y` ints). Ints convert implicitly to the value types; there is no conversion back — read `.Value` explicitly. Counts (quantities, rounds, indices) stay plain `int`.
- **Keep the domain value types out of hot loops.** The value types' operators are not inlined by the Tier0 JIT and the console app never gets far enough into Tier1 for it to matter, so per-node/per-candidate operator calls measurably slow the planners (the performance results guard this). Public APIs take `Centimeters`/`SquareCentimeters`/`Point`, but engine internals stay raw ints: `RoundOccupancy` converts at the method boundary (public `IsFree/MarkOccupied/MarkFree(Point, Centimeters, Centimeters)` over private `IsFreeCells/...` int methods), `MaxRect`/`GRect` and the exact planner's per-node area state are raw ints, and `SlotOrder` reads `Position.X.Value`/`Y.Value`. Do not "clean these up" into value types — `tests/GrillMaster.PerformanceTests` (committed `performanceResults.json`, +50% speed gate) is what catches the regression.
- No try/catch in the request path: API failures surface as the raw .NET exceptions (`HttpRequestException` for transport/non-2xx, `JsonException` for malformed bodies) and are let to reach the top (unhandled → non-zero exit). The only top-level catches are in `Program.Run` (`GrillMasterException` and `OptionsValidationException` → logged error line + exit 1). The mock base is `GrillMaster.Core.Testing/Infra/ApiMock` (owns/disposes the `WireMockServer`, exposes `Url` as `Uri`).
- Assertions use AwesomeAssertions (`Should()`), never xunit's `Assert` — in every test project.
- Namespaces must match the project/folder layout — IDE0130 is enforced: the namespace is the project `RootNamespace` plus the folder path under the project root (e.g. `src/GrillMaster.Application/Features/Plans/Planners/` → `GrillMaster.Application.Features.Plans.Planners`).
- Logging goes through `[LoggerMessage]` partial methods (e.g. `private static partial void LogX(ILogger<T> logger, ...)` with the message template in the attribute), not inline `logger.LogXxx(...)` calls.

## Branching & PR workflow (dev → main)

- **All work happens on the `dev` branch.** Commit directly to `dev`; do **not** create feature/topic branches that open a PR straight to `main`.
- `main` only ever changes via a merged **`dev` → `main`** PR. There is exactly one PR in flight at a time, from `dev` to `main`.
- The loop is: commit on `dev` → push `dev` → open (or update) the `dev` → `main` PR.

When creating or updating the `dev` → `main` PR:

1. **Always run `git fetch origin main` first** — this is critical. The local `main` branch is often outdated and will show stale committed changes as part of the diff if not refreshed.
2. Compare `origin/main..dev` to identify only the actual new changes.
3. Check if a PR already exists (use `github_list_pull_requests`).
4. If none exists, create one with an accurate title and description summarizing the changes.
5. If one exists, update its title and description to reflect the actual current diff.
6. **Stop there. Never merge the PR (no `gh pr merge`, no merge via the API).** The user reviews the diff and merges it themselves; merging on the user's behalf defeats the review.
